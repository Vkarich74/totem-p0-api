## Exact database event flow
1. Operator's existing /send-email or /resend-email route checks Admin access, existing market rules and request. Only status=email_ready without a prior message_id or welcome key may claim a new send. Historical email_failed with message_id is blocked from replay.
2. US email is gated by verified, current T2/T3 Odoo paid evidence + exact company4/site5/partner/source/role/owner + existing Geo in a trusted row lock. Odoo HTTP occurs outside open SQL transaction; DB clock checks short-lived paid receipt in transaction.
3. BEGIN; SELECT owner_opening_requests FOR UPDATE; find any existing welcome messages by deterministic key; INSERT public.messages pending with stable owner_opening:<request_id>:welcome:v1 using ON CONFLICT(idempotency_key) WHERE idempotency_key IS NOT NULL DO NOTHING; INSERT traces pending; bind request.message_id and preview via CAS; write audit; COMMIT. No Gmail called on rollback.
4. After COMMIT, build MIME with deterministic RFC Message-ID <totem-owner-opening-<id>-welcome-v1@totemv.com>, call the EXISTING Gmail OAuth client API exactly once.
5. Gmail accepted + message id -> short BEGIN; lock owner then message; compare-and-set existing message sent and owner status email_sent/email_status sent; trace and audit in same COMMIT. Gmail API acceptance is not a guarantee of inbox delivery.
6. Unknown Gmail outcome or failed PostgreSQL final COMMIT -> best-effort transition to messages.data.delivery_state=uncertain and existing owner status email_failed, email_status failed, error OWNER_OPENING_GMAIL_DELIVERY_UNCERTAIN. Crucially, if even that DB update fails, the first committed stable key remains and rejects all replays. Never automatically resend after ambiguity.
7. Reconciliation requires actual Gmail SENT metadata proof on the same deterministic RFC Message-ID, same sender and original stored recipient, by provider internal gmail_message_id. Positive proof updates the SAME intent as sent in one Core transaction with traces and audit. Negative proof, no read scope, Gmail timeout or missing ID => remain blocked; no mail sent by reconcile endpoint.

The reconciliation endpoint requires the existing AdminRuntimeGuard. Gmail metadata GET requires suitable Gmail READ authorization in the existing OAuth credentials; send-only scope may be insufficient. Do not change scopes/credentials or enable any Production feature without separate approval. For unknown provider id, an authorized operator may use Gmail Sent search by deterministic RFC Message-ID to recover the provider id, then call the protected reconciliation endpoint. Absence from Gmail search is NOT proof of non-delivery; no automatic resend is permitted.

## Safety constraints
- No credentials or real recipient data added in source tests; no test Gmail messages sent.
- Duplicate Admin button, resend endpoint, process crash, Gmail timeout, lost API ACK and failed DB COMMIT do not produce a second automatic send.
- Exactly-once external Gmail delivery is not technically guaranteed; at-most-once automatic send attempt is the intended invariant for a committed logical key.
- A welcome may remain blocked pending manual verification when the process crashed after claim but before sending: this favors no duplicates over guaranteed delivery.
- Existing KG historical email_failed resend behavior becomes fail-closed if a prior message_id exists; KG production regression and operational training must pass before deployment.
- Frozen US intake 409 and CRM14 OFF are preserved; no Odoo automation, payment, new account or subscription operation is activated.
